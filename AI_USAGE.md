## How I used them

1. In chat, I gave Claude the assessment and had it write `CLAUDE.md`, so Claude Code would know the rules before writing anything.
2. In Claude Code, I built in the order `CLAUDE.md` sets: test runner, types and seed data; then tested logic; then state and persistence; then the five screens; then docs.
3. I ran the app in Expo Go on my phone and checked behavior myself, instead of trusting a summary that said it worked.
4. I used chat again to review the finished code, which found real bugs (see below).

## Three prompts and agent directions

**1. The project rules in `CLAUDE.md`**

> "Do not fake results. No hard-coded outputs that only pass the examples, no fabricated benchmarks, and no weakened or altered tests."
> "Keep business logic out of screens and presentation components."
> "Pass the current time into logic functions. Do not call `Date.now()` inside `src/logic/`."
> "Put persistence behind a small storage interface so tests can use an in-memory fake and simulate failures."

Why it mattered: it set the architecture before any code existed. What it produced: no `Date.now()` anywhere in `src/logic/`, and time passed in as `now`. A `KeyValueStore` interface with an in-memory `memoryStore` that can be told to fail reads or writes. Screens that read hooks in `src/state/derived.ts` instead of pricing anything themselves.

**2. The foundation prompt (build step 1)**

> "Read CLAUDE.md and complete only build order step 1: the test runner, data types, and seed data. ... Create a deterministic seed generator in scripts/ and generated seed data in fixtures/. Meet every Seed data minimum in CLAUDE.md, and include each required messy case. Document the record formats in fixtures/README.md. ... Do not build screens or business logic yet. Run npx tsc --noEmit and npm test, fix any failures, and report the real results."

Why it mattered: the data model shapes everything after it, and "only step 1" kept Claude Code from building screens on guesses. What it produced: `fixtures/seed.json` (93 products, 3 retailers, 15 pantry items, 3 lists, 2 profiles, 2 ZIPs, 6 trips), `scripts/generate-seed.js` (byte-identical output every run), `fixtures/README.md` listing each deliberate edge case, and a CI step that fails if regenerating the seed changes the file.

**3. The per-screen prompt**

> "Read CLAUDE.md, the Project requirements, and design-system/. Then build the [screen] screen. Follow the Track E requirements for this screen, including its loading, empty, and error states. Put all business logic in separate, testable functions, not in the screen. If the logic this screen needs doesn't exist yet, build and test it first."

Why it mattered: it forced logic and tests to exist before the screen that uses them. What it produced: all five screens have real empty states ("Nothing to compare", "No new picks right now", "Nothing to restock", "Your pantry is empty", "No trips yet"), and every screen gets its numbers from `src/logic`.

## Debugging with AI

**1. Expo Go timed out on my phone.**
- Symptom: the app only ran with `npx expo start --clear --tunnel`. A plain start timed out on every network.
- The AI's first guesses were a VPN, the firewall, and a wrong IP. None fit.
- What cracked it: the `exp://` address started with `172.19`, and I told it I run Expo inside WSL2. WSL2 sits on its own virtual network that a phone can't reach, which explained why only the tunnel worked.
- Workaround: `--tunnel`, which runs the same build in Expo Go. It's in the README setup section. I also turned on WSL mirrored networking, which moved the address from `172.19.x.x` to `10.14.29.0`. The problem was the network path, not the app.
- A side mistake of mine: I once typed `npx exp start` instead of `npx expo start`, which launched an old deprecated CLI and printed unrelated SDK errors.

**2. Reviewing the code by reading it.** A chat session said the app "looks done" after reading the repo without running anything. I said that couldn't be right, so it reviewed the code properly and found four defects (listed below). In the cloud session I reproduced the first one with a throwaway test: adding 1 gal to a row holding 1 fl oz produced `quantity=2 unit=fl_oz`, and the correct answer is 129 fl oz. I confirmed the other three by reading the code. The throwaway test was deleted and is not part of the repo.

**3. Checking everything before writing docs.** Before documenting anything, the cloud session ran the real commands on a clean install: `npm ci`, typecheck, lint, `npm test` (110 passed), the seed generator (no diff in `fixtures/`), and a web bundle build. All passed. Demo numbers (basket totals, restock suggestions, discovery picks) were checked against the real logic with temporary tests, then those tests were removed.

## Corrections to AI output

1. **"Looks done" was an overclaim.** See debugging item 2. Pushing back led to four real defects being found.
2. **Pantry rows jumped around.** The pantry was sorted by days left, so editing a quantity or advancing the clock moved rows while I was using them. I changed it to a stable newest-first order (commit `74c2640`). `pantryRows` in `src/logic/pantry.ts` explains why, and a test, "pantry rows show newest first and never move when stock changes", covers it.
3. **Errors in the AI-written docs, caught on re-check.**
   - The README said double taps are handled "by id, not by disabling buttons". That was wrong: the Complete trip button is also disabled after a trip is saved. It now says both.
   - `SCALE_AND_COST.md` had two arithmetic slips: 40K reminders a week is about 175K a month, not 160K, and 6,800 users at 2,000 a week takes about 6 weeks with the 14-day window, not 4. Both were fixed.
   - The first `DEMO.md` draft said a restock suggestion would show on the Kitchen screen when it wouldn't, because items already on the active list are left out. A probe against the real seed showed the right suggestions, and the script now uses those.

## Known defects (not fixed)

Found in the review above. They are not fixed in this submission, and I would rather list them than hide them.

| # | Where | What happens |
|---|---|---|
| 1 | `ADD_LIST_ITEM` in `src/state/reducer.ts` | Merging an item already on the list adds raw numbers without converting units. 1 fl oz plus 1 gal gives 2 fl oz, not 129. Reproduced with a test. |
| 2 | `completeTrip` in `src/state/app-state.tsx` | The pantry gets the list quantity, not what was bought. 1 lb of rice bought as a 5 lb bag adds 1 lb. |
| 3 | `src/state/app-state.tsx` | If reading storage fails, the app starts from the seed and then saves the seed over the old data. A notice is shown, but the old data is lost. |
| 4 | `src/app/(tabs)/compare.tsx` | The Compare tab stays mounted, so `basket_compared` can fire when the list is edited from the List tab. |

None of these break the required reviewer flow, but 1 and 2 can make quantities and pantry stock wrong in edge cases, and no existing test covers them.

## Decisions

**Proposed by the AI, which I reviewed and kept**
- AsyncStorage for persistence, behind a swappable storage interface.
- Prices older than 7 mock days are stale. Track E sets no limit, so this rule came from another track in the PDF. Stale prices are flagged but still used.
- Compare opens from the List tab. The mock clock and event log live on the Trips tab.
- Request ids and revision-based trip ids, so a repeated tap or a second "Complete trip" is ignored.
- An incomplete basket is never "Best deal", even when it is cheaper.
- A pinned brand beats a cheaper product, and the cheaper one is shown with the savings.
- Retailer handoff is simulated. Nothing opens and nothing is ordered.

**Mine**
- I did not accept "looks done" from a summary, and had the code reviewed and checked.
- I stopped tracking `CLAUDE.md` and `AGENTS.md` in the repo (commit `d9c771f`).
- I changed the pantry to a stable order after seeing it jump around in use (commit `74c2640`).
- I added CI even though the brief doesn't ask for it.
- I kept the four defects in this file instead of leaving them out.
